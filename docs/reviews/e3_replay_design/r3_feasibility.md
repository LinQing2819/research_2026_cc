# 第三轮：代码适配、数据可得性、上下文与总成本

日期：2026-10-26。评审者：本会话主代理。
对象：CVS-P2；依据当前v0.2.1实现、E2分析文件及R1/R2发现。
不是通用代码审查或真实运行验收，本轮未修改执行代码、未连接/启动生成服务器。

## 判定

**HOLD_IMPLEMENTATION_AND_GENERATION**。
可以继续零模型调用的数学研究、结果诊断与协议设计；
目前既不应实现在线部分提交，也不应安排多版本全表实验。
主要阻断：新颖性增量未明确、独立数据未就绪、完整算法未冻结、功效/总成本未闭合。

## 1. 当前资产能复用什么

可复用：

- 官方纯prompt builder、冻结规则/经历提取思路；
- 单独检索和独立packing、完整token IDs比较；
- 8192上下文、5888输入、2048输出、256余量；
- 单请求持久计费、原payload/seed恢复、阶段封存原则；
- `.venv-client`客户端、`.venv-vllm`服务、CPU embedding、screen启动约定。

不能直接复用为新方案：

- `common.py`固定七臂和V5身份；
- `source.build_snapshots`固定两个边界；
- `study.py`固定dev/test流程及特定selector授权；
- `qualification.py`针对旧Engineering数据、三对候选和旧槽身份的批准记录；
- `component-v4.sqlite`作为新研究预算。

把新的25格循环塞进原E2的run，会改变已经完成的研究含义与身份。
正确方向是将新研究作为独立协议/入口/预算实现，旧代码版本与账本封存保留；
当前没有实现许可，故本轮不做该重构。

## 2. “部分提交”不能从冻结prompt能力直接推出

读取了官方ExpeL-Online-ST的observe/restore路径：

- observe维护规则计数、最近成功batch、经历池及pending rollout；
- restore从渲染规则重建，逐条将计数设为1；
- restore重放经历，但不能据此保证最近成功batch等闭环状态完整恢复；
- 通用runner的seed/resume还会移除`memory`字段。

这些是此前已记录的限制，本轮只重新核对，不认定为这次新增缺陷。

因此R3要求把首阶段名称改为**冻结版本组合选择**。
若未来要在线部分提交，需要定义：

1. 规则内容、支持计数、待更新batch、经历及向量的完整状态schema；
2. 拒绝规则但保留经历后，下一次consolidation以什么为输入；
3. 部分提交与自然轨迹的区别、未来学习如何计费；
4. 崩溃恢复前后，同请求与下一步更新的一致性；
5. 新旧方法是否使用各自真实闭环轨迹，不能共享一个方法创造的未来轨迹冒充自然比较。

没有该合同，宣称可部署的在线更新方法属于过度外推。

## 3. 当前详细数据仍不足

本机`.cache/e2-analysis.json`已核验封存值、汇总及选择器算术；
包含158题的组件摘要，不含逐题score/原始回答/每条finish reason。

下一步需要只读取得已完成实验的：

- SQLite一致性快照（应通过backup API或停写后合法checkpoint再复制，不能漏WAL）；
- manifest及selection/preflight/smoke绑定产物；
- 必要的questions、scoring_gold和旧prefix来源，用于独立评分/边界核验。

只读导出字段至少为phase、qid、arm、rep、score、predicted、finish_reason、usage、
result/raw/request hash。字段摘要够做得失统计；原始响应和来源还用于独立重评分。
不能只拿一个summary hash说已经完成完整运行审计。

新历史数据也尚不存在。原E0已看过的题不能改名为新研究的确认集。
真实新数据拆分、语义去重与完整源检查都在生成前完成；失败不自动换题。

## 4. 上下文可控，但总评估成本不能忽略

多版本是多个独立请求，不把所有版本装进单次prompt：
每条继续维持8192总窗口及分组件限额。
K=4时每题最多25个配置，最多输出25次，单请求不超限不等于总成本低。

按已测E2正式回答平均3338.84 tokens/请求作**线性估算**：

| 示例，不是批准配置 | 求解调用数 | 相当于E2次数 | 按旧均值估算tokens |
|---|---:|---:|---:|
| 2条历史，25格，dev32＋test96，每格2次 | 12,800 | 5.79倍 | 约4274万 |
| 6条历史，25格，dev64＋test256，每格2次 | 96,000 | 43.40倍 | 约3.21亿 |
| 6条历史，25格，dev64＋test512，每格2次 | 172,800 | 78.12倍 | 约5.77亿 |

上述还没有加构建历史、规则更新、独立验收V、探测、重试。
不能把这类扩展描述为“再跑一晚”。现有analysis没有wall time，不能据此给出可靠小时数。

### 修订：只评估各策略最终选出的少量配置

避免给所有25格都生成完整T，可以把搜索与最终测试分开。
但是多个算法的搜索也要付费，不能只算本方法一份预算：

六个需要选择数据的算法（P2、均匀、直接搜索、通用低秩、二阶适配、整库选择），
另加四个固定策略（NN、固定旧R新E、纯经历、ZZ），最终最多10个不同配置。
每个算法每历史搜索＋验收调用上限b，T有n道题、每题r次，
未计共享复用前的示例求解上限为：

`H × (6b + 10nr)`。

| 修订示例，仍非批准配置 | 调用数上限 | E2倍数 | 旧均值tokens估算 |
|---|---:|---:|---:|
| H=2，b=512，n=128，r=2 | 11,264 | 5.09倍 | 约3761万 |
| H=6，b=1024，n=256，r=2 | 67,584 | 30.55倍 | 约2.26亿 |

每请求输入＋输出预留最大7936，后一示例仅求解预留上限约5.36亿tokens。
这些算术说明规模修订仍未解决成本，而不是新建议用户支付的预算。
重复配置、共同查询的复用可以降低实际调用，但必须提前规定共享和统计相关性。
各策略的虚拟授权成本与整个benchmark实际生成总量分别报告。

此外，b中如果留给独立V的题太少，就触发R2的低功效问题。
先定一个便宜b再宣称足以确认3pp，不能通过评审。

## 5. 可以立即做的工作

G0的新增生成上限为**0**，新增模型训练为0，新增服务器运行任务为0。

1. 获取并核验已有逐题结果，解释dev授权前31题与完整dev的差异；
2. 整理真实prompt变化、得失、输出截断与检索替换；
3. 数学反例与可复现数值研究，检验结构方法被哪些情形击败；
4. 冻结方法采集规则、强基线接口和成本计费；
5. 根据原始结果的方差及新目标，完成真实预算/功效表，再回到R2/R3复审。

新增实验代码、离线仿真算法实现也应等方法定义和对应实现范围明确后进行；
本轮的公式计算不是P2算法实现。
不为了省开发时间恢复旧逐题gate、忽略无记忆对照或使用错误的旧CS。

## 6. 进入实现前的硬条件

- [ ] P2相对同候选通用低秩/直接搜索的独立增量写清；
- [ ] 算法拟合、采集、随机探索比例、降级条件、验收规则完整冻结；
- [ ] 构建/S/V/T与跨历史依赖设计通过审查；
- [ ] 全部阶段成本和功效与资源上限一致；
- [ ] 冻结组合选择与在线状态提交明确分开；
- [ ] 旧实验只读保留，新入口不重置旧预算；
- [ ] 可自动串联smoke到正式运行，失败停止，screen与日志从第一步配置。

这些是当前真实未满足项，不是请用户口头同意就可跳过的形式审批。

**R3结论：复杂版尚未达到可实施状态；放行G0的数据/数学工作，
继续保留实现和生成阻断，不能用“先编码再说”补齐科研缺口。**
